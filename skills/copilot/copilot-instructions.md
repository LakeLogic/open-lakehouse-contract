# Open Lakehouse Contract (OLC) — GitHub Copilot instructions

This repository uses **Open Lakehouse Contracts** (`*.olc.yaml`): one YAML file per data
product declaring schema, quality (SQL rules), PII/masking, lineage, materialization, and
SLOs, executed by a conforming runtime. **Intent lives in the contract; the engine is a
flag chosen at apply time.**

When creating or changing data products, or reviewing a change that touches data:

- **Validate** every contract against `schema/open-lakehouse-contract.schema.json` — run
  `olc validate <path>` (or `python scripts/validate.py <path>`) and fix each reported
  `location: message` error until it passes.
- **Stay SQL-native**: quality rules and transforms are SQL (`sql: "amount > 0"`), not
  bespoke check objects.
- **Never hard-code the engine**: `materialization` sets `strategy` + `format`; the
  provider is chosen at apply time, never inside the contract.
- **Preserve intent on changes**: keep `primary_key`, `quality`, `materialization`, `pii`,
  and `service_levels` satisfied — or change the contract deliberately and flag the
  breaking diff (a `merge` silently becoming `append`, a dropped rule, a widened PII field).
- **Persist requirements** in the contract, not in a chat message.

**Verbs (data-native workflow):** `discover` → `contract` → `review` → `validate` →
`impact`. When asked to review a PR that touches data, act as the merge gate: compare the
change to the applicable contract and answer PASS/FAIL — "does the data product still
satisfy its contract?", not just "did the code change?"

## Where things go

These are the placements agents most often get wrong; the validator rejects the wrong ones.

```yaml
model:
  fields:
    - {name: order_id, type: integer}    # no `primary_key:` or `unique:` on a field
    - {name: line_no, type: integer}
primary_key: [order_id, line_no]         # TOP LEVEL, a list — never under `model`
quality:
  dataset_rules:                         # `unique` is a DATASET rule, never a row rule
    - unique: email                      # one column
    - unique: [order_id, line_no]        # composite key
    - unique: {field: email, severity: warning}      # mapping: exactly one of
    - {name: sku_unique, unique: sku}                #   field | columns; labels
                                                     #   (name, severity, category,
                                                     #   description) beside or inside
```

- `primary_key` makes a conforming runtime check the key is unique (LakeLogic adds a
  `<keys>_unique` dataset rule). Do not repeat it: a `unique` rule, or a
  `COUNT(DISTINCT …)` SQL rule, over the same columns is treated as that check.
- `unique` mapping keys are only `field`, `columns` (alias `fields`), `name`, `severity`,
  `category`, `description`. Anything else (`column:`, `key:`) is rejected.


## Common shapes

```yaml
quality:
  fail_pipeline_on_dataset_error: true
  row_rules:                       # checked per row; failing rows are quarantined
    - not_null: [trip_id, pickup_at]
    - accepted_values: {field: status, values: [completed, cancelled]}
    - name: fare_non_negative
      category: validity           # completeness | uniqueness | validity | consistency | accuracy
      description: Fares are never negative
      sql: "fare_amount >= 0"
      severity: error
  dataset_rules:                   # checked once per run, over the whole dataset
    - unique: trip_id
    - row_count_between: {min: 1}
    - name: dropoff_after_pickup
      category: consistency
      sql: "SELECT SUM(CASE WHEN dropoff_at < pickup_at THEN 1 ELSE 0 END) = 0 FROM source"
transformations:
  - phase: pre
    sql: "SELECT * FROM source WHERE trip_id IS NOT NULL"
  - phase: post
    derive: {field: duration_minutes, sql: "date_diff('minute', pickup_at, dropoff_at)"}
```

There is no `rules:`, `type:`, `assertion:`, `checks:` or `tests:` key anywhere in a
contract. Unknown keys are rejected.

## Writing to a database

A contract can write to a database as well as to cloud storage. When it does, write its
**quarantine** and **run log** to a database too. Never leave rejects or logs unwritten because
the target is not cloud storage.

**`format: database`** - the runtime's native writer: a bulk load and one upsert statement per
batch, in one transaction. Postgres, MySQL / MariaDB, SQL Server / Azure SQL, DuckDB, SQLite.
The fast choice for frequent loads (a 1,200-row merge in ~0.02 s on Postgres, unchanged rows
not rewritten).

```yaml
# a contract
primary_key: [symbol, ts]              # needed for merge and on_conflict: ignore
materialization:
  format: database
  connection: env:PG_URL               # postgresql:// | mysql:// | mssql:// | duckdb:/// | sqlite:///
  table: market_data.market_bars       # schema.table, created when missing
  strategy: merge                      # append | merge | overwrite   (scd2: use format: dlt)
  write: {only_changed: true}          # optional: on_conflict, only_changed, batch_size,
                                       #   create_table, allow_empty_overwrite
quarantine:
  format: database
  connection: env:PG_URL
  table: quarantine.quarantine_market_bars
```

```yaml
# _system.yaml (or the contract's metadata) - the run log
metadata:
  run_log_backend: database
  run_log_table: lakelogic.run_logs
  run_log_connection: env:PG_URL       # defaults to materialization.connection
```

**`format: dlt`** - any destination dlt supports (and API sources). Slower per write.

```yaml
materialization:
  format: dlt
  dlt_destination: postgres            # postgres | mssql | snowflake | bigquery | duckdb | …
  dlt_credentials: env:PG_URL
  dlt_dataset_name: silver
quarantine:
  format: dlt
  table: quarantine_orders
  dlt_destination: postgres
  dlt_credentials: env:PG_URL
```

- `connection` / `dlt_credentials` are references (`env:NAME`, `${ENV:NAME}`, `keyvault://…`),
  never values.
- A failed dataset rule can set the batch aside (`quality.on_dataset_failure: quarantine`), or only
  the failing groups (`quarantine_scope: [symbol]`); the rest of the batch is still written.


## Business map

Business names live in the domain file; contracts refer to them by name. Do not copy a
definition into a contract.

```yaml
# _domain.yaml — domain-only (never _system.yaml)
concepts:
  Trip:                                  # the business name contracts refer to
    definition: One ride from pickup to drop-off.
    identifier: trip_id                  # one column
    also_called: [ride, fct_trip]        # keep the old technical name when renaming
relationships:
  - {from: Rider, verb: books, to: Trip, cardinality: one_to_many}   # or unknown — never guess
```

```yaml
# a contract
entity: Trip                             # TOP LEVEL — never under `info`
model:
  fields:
    - {name: rider_id, type: string, identifies: Rider}
    - {name: payer_id, type: string, identifies: Customer, role: payer}
```

- Concepts, links and names you infer are **suggestions**. Propose them as a change to
  `_domain.yaml` for a person to merge; never write them as agreed.
- When editing `_domain.yaml`, change only `concepts:` / `relationships:` / `story:` and
  leave comments, headers and the rest of the file untouched.
- A date dimension (`date_key`) is not a business relationship; do not link concepts
  through it.

## Ingest a database table into the landing zone

`ingest-database-to-landing` · ingest · load patterns: full, incremental

A table in PostgreSQL, MySQL, SQL Server / Azure SQL, Oracle or SQLite should be copied into the lakehouse's landing zone as files, a full copy first and only new or changed rows after that.

```yaml
version: 1.0.0
dataset: '{source_table}'
info:
  title: '{source_table} from {source_system}'
  target_layer: bronze
  system: '{source_system}'
source:
  type: database
  path: env:SRC_DB_URL
  load_mode: incremental
  watermark_field: '{watermark_column}'
  options:
    fetch_size: '{fetch_size}'
model:
  fields:
  - name: id
    type: long
    required: true
    description: Replace with the table's own columns, or let Studio draft them from
      the table.
  - name: '{watermark_column}'
    type: timestamp
    description: When the row last changed; each run reads only rows newer than the
      last one read.
materialization:
  strategy: append
  target_path: '{landing_path}'
  format: parquet
metadata:
  run_log_table: '{run_log_table}'
```

| Parameter | What it is | Expected format | Example | Secret | Set in |
|---|---|---|---|---|---|
| `SRC_DB_URL` | How to connect to the source database. | `<dialect>://<user>:<password>@<host>:<port>/<database>` | `postgresql://ingest:****@pg-prod.postgres.database.azure.com:5432/sales?sslmode=require` | yes | environment variable (or a key vault secret exposed as one) |
| `source_table` | The table to copy, schema-qualified where the database needs it. | `<schema>.<table>` | `public.orders` | no | contract |
| `source_system` | The system the table belongs to; names the landing folder and the bronze table. | `snake_case name` | `erp` | no | contract |
| `watermark_column` | A column that grows when a row is added or changed, so later runs read only new rows. | `a timestamp or ever-increasing number column of the source table` | `updated_at` | no | contract |
| `landing_path` | The folder in the landing zone the files are written to, one folder per table. | `<landing_root>/<system>/<table>` | `abfss://landing@mystorage.dfs.core.windows.net/erp/orders` | no | _system.yaml environment ({landing_root}) — a different place per environment |
| `fetch_size` | Rows fetched per round trip to the database — how much the source serves at a time. | `a whole number of rows; size it to the row width and the database tier` | `10000` | no | contract (source.options.fetch_size) |
| `partition_column` | Optional — read in parallel slices of this column (Spark and Polars only). | `a numeric or date column with an index, e.g. the primary key` | `id` | no | contract (source.options.partition_column + partition_num), only when one connection is too slow |
| `run_log_table` | Where each run records how far it read (the watermark), so the next run starts there. | `<schema>.<table> on the platform; run_log_dir / run_log_path (a folder or JSON file) also work` | `lakelogic.run_logs` | no | contract — in a Studio project the project's _system.yaml sets it for every table |
| `storage login` | How the run signs in to the landing storage. | `AZURE_STORAGE_ACCOUNT + (AZURE_CLIENT_ID, AZURE_CLIENT_SECRET, AZURE_TENANT_ID) or AZURE_STORAGE_ACCOUNT_KEY; AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY for S3` | `AZURE_STORAGE_ACCOUNT=mystorage` | yes | environment variables |

**Before you run**

- Set SRC_DB_URL where the pipeline runs (environment or key vault).
- Allow the pipeline's network address through the database firewall.
- Give the pipeline's identity write access to the landing folder.

**What a design-time test proves:** Studio checks the contract and runs it on generated rows written to a sandbox folder; it never connects to your database or writes to your landing zone. The first real run is yours.
